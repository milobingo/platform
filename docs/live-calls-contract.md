# LiveKit call contract

All writes use same-origin JSON and `X-Vlampie-Call: 1`. Every call request supplies `gameId`, `role` (`host`, `player`, `output`) and `clientId`. Actions also supply `callId` except `prepare`. Writes from the host use the regie client that prepared the call; reads remain available for recovery. After the original host heartbeat has expired (20 seconds), the same authenticated owner may explicitly confirm-return/resume-draw from a new regie client; that recovery action atomically rebinds the host while preserving the hold.

- `GET /api/livekit/settings`: owner-only safe settings `{url,apiKey,apiKeyConfigured,secretConfigured,configured,revision,connectionTest:{tested,testedAt,roomCount?}}`. The API secret is never returned.
- `POST /api/livekit/settings`: `{url,apiKey,apiSecret,revision,action:'save'|'test'}`; a blank secret preserves the saved secret. `action:'test'` really calls LiveKit `ListRooms`; only a successful upstream response returns `tested:true`. Changed credentials reset the previous test. Credentials cannot change during an active call.
- `POST /api/livekit/preflight`: selected family's `{gameId,profileId}` returns `{url,token,room,identity,role:'player',target:'preflight',allowedRemoteIdentities:[],expiresAt,simulated:false}`. This token permits neither publishing nor subscribing, expires after 60 seconds and creates no OpenAI session. Connect and disconnect promptly. Request microphone permission separately in the browser.
- `GET /api/live-calls?...`: `{call,serverTime}`; the host also receives the durable `cues`. Families get only their own call. An owner can read the active owner call from another show for recovery; mutations must use that call's own `gameId`.
- `POST /api/live-calls`: `{action,...}` → `{call,serverTime}`; the host response may also contain `game`.
- `POST /api/live-calls/token`: same identifiers plus `target:'backstage'|'live'` → `{url,token,room,identity,role,target,expiresAt,participantIdentity,guestIdentity,outputIdentity,hostIdentity,allowedRemoteIdentities}`. `guestIdentity` aliases `participantIdentity`. Clients strictly accept remote tracks only from their returned allowlist. Tokens expire after 120 seconds.
- `POST /api/live-calls/realtime`: output only, phase `live`, explicit `mode:'ai'`, `{sdp}` → `{sdp,realtimeId,serverTime}`. There is at most one AI session per call. No AI session before live or in prepared mode; default model `gpt-realtime-2.1-mini` uses the central server-side OpenAI key and the frozen presenter's voice/personality.
- `POST /api/live-calls/realtime-stop`: bound output only; closes its stored AI call. A stale output lease does not prevent teardown. Host cleanup also closes it on termination. A late creation response is immediately closed; an upstream cleanup failure stays retryable and keeps the draw hold.

## State and visibility

`preparing → ringing → backstage → staged → live → returning → returned → completed`.

Refusal, no answer, cancellation, failure or heartbeat loss enters `returning` with `outcome`. The draw hold persists. Only an explicit successful `resume-draw` releases it. Switching from backstage to live temporarily exposes `switchingLive:true`; it is an intentional room teardown, not evidence of a failed call.

The safe snapshot contains `id,version,transport:'livekit',gameId,brandId,entryId,profileId,name,characterId,characterName,realtimeVoice,phase,outcome,reason,createdAt,updatedAt,maxSeconds,ringUntil,liveUntil,muted,drawHeld,checkpoint,context,checks,returnState,media,realtimeStatus,realtimeStopped,voiceLevel,switchingLive,resourcesClosed,cleanupError,simulated:false` and opaque room participant identities. Optional timestamps include `liveAt,endedAt,completedAt`. It contains no API secrets, tokens, account identifiers or private character book.

- `checkpoint = {id,epoch,drawnCount,lastNumber,drawn}`.
- `context = {callName,pronunciation,reason,note,confirmedFacts}`. Only the host sees `note`. Only canonical server results produce `confirmedFacts`; client claims cannot create wins/prizes. Context is frozen when the call goes live and replaced for every next caller.
- `checks = {hostConnected,playerConnected,outputConnected,soundChecked,explanationGiven}`.
- `returnState = {playerConfirmedAt,hostConfirmedAt,method,note}`. Only the host sees the manual return note.
- `media = {host:{connected,micReady,audioReady?},player:{connected,micReady,audioReady?},output:{connected,micReady?,audioReady}}`.
- `realtimeStatus` is absent before creation, then `starting`, `ready` or `failed`. `ready` confirms the server SDP exchange; browser media and playback readiness still require real checks.

## Actions

1. Host `prepare`: `{entryId,characterId,maxSeconds,context:{callName,pronunciation,reason,note}}`. Claims the single owner call, freezes the presenter and atomically installs `game.state.drawHold`. It does not pause the whole show or use legacy `state.callId`: entertainment can continue. Pending draws, open bingo windows and unacknowledged results reject preparation.
2. Host `ring`: enters `ringing`, with a 90-second answer window so the participant can catch up with delayed YouTube. This timeout is never playback proof.
3. Player `answer`: `{checkpointId,cardsUpdated:true,heardLastNumber:checkpoint.lastNumber,youtubeMuted:true}`. The UI must first verify hearing the last number, updating the cards and actually muting/removing YouTube. The answered device is bound to this call; phase becomes `backstage`.
4. Any bound role `heartbeat`: `{connected,micReady,audioReady,target,failed,voiceLevel?}` reports real local media state. Failure enters `returning`; the hold persists. Expected backstage disconnects during `switchingLive` do not fail the call. An output live heartbeat can include actual microphone/presenter `voiceLevel`; the server bounds it to 0–1 for studio lipsync, and resets it on return.
5. Host `backstage-ready`: `{soundChecked:true,explanationGiven:true}` requires connected host/player microphones and records the checks. The phase remains `backstage`.
6. Host `stage`: after the checks, transitions to `staged`. Host `context` edits `{context:{callName,pronunciation,reason,note}}` before live; an edit clears sound/explanation confirmation and returns a staged call to `backstage`.
7. Host `go-live`: `{contextConfirmed:true}`. The server first revokes both backstage identities and deletes the private room, then enters `live`. The output never has a private-room token. The host is subscribe-only in the live room. The output waits for real selected-player audio/readiness before starting OpenAI. A live phase alone does not prove working audio.
8. Host `mute`: `{muted:boolean}` changes actual Cloud publishing permission and the local output gate. Unmuting requires the player client to restore its microphone publication.
9. Host/player `finish`: ends backstage/staged/live into `returning`. Host/player `cancel`, player `decline`, any role `fail` also retain the hold. End/failure cleanup closes rooms and AI; failed cleanup is visible and retryable.
10. Player `player-returned`: `{confirmed:true,checkpointId,youtubeReady:true,youtubeAudible:true}` or `playbackInfo:{ready:true,audible:true,...}` after restored playback. Explicit parent confirmation is supported when the iframe API is unavailable; a timer alone is insufficient.
11. Host `confirm-return`: `{confirmed:true}` after player confirmation enters `returned`. Without it, `{confirmed:true,manual:true,note:'meaningful verification ...'}` records how the regie actually checked the return. No draw release yet.
12. Host `resume-draw`: requires `returned`, host confirmation, completed resource cleanup and the same authoritative hold. It releases `drawHold` and completes the call. It never automatically draws a number. An open bingo window remains protected.

Fresh studio output ownership is required for preparation, going live and creating media. Returning and resuming remain possible after an output failure. Backstage rooms accept only host and selected participant. Live rooms accept only selected participant, output and a subscribe-only host. All publishing is microphone/audio only; data publishing is disabled. Room names and participant identities use opaque call identifiers, never child names or email addresses.

## Milo: durable rundown cues and prepared magic

Vlampie's existing workflow remains separate. Milo rounds optionally set `callFullCardWinner:true`; absence means off. Only the first acknowledged canonical final full-card main-prize result creates `winner:<resultId>`. Intermediate patterns, consolation and losing finalists never create it. The winning child comes from the immutable result. The cue waits in `waiting-announcement` until the bound program output reports the exact official winner script ended while rendering the winner scene. A voice receipt cannot authorize another round's result.

New Milo plans and the premiere contain two `random-call` blocks after rounds 1 and 3. Existing documents are not changed on read. Drafts expose an explicit add button. When calling is enabled, a new draft requires exactly two blocks; the server will never start a third random cue. Winner calls are separate. An adjacent random cue yields to the winner and waits for a later planned safe pause, or is skipped with a reason.

`game.callCues` contains the durable schedule/selection/outcome, and `game.callHistory` records actual invitations. Both are owner-only. They are separate from per-child consent and current presence. Random selection uses unique participating account/profile pairs, not books or tabs. Prior invitations exclude a child from further random selection, but never exclude a later official winner. Selection is persisted before provider checks and is never rerolled on retry. Current per-show consent, admitted participation, recent app presence (45 seconds), microphone/headphone/connection checks and a recent technical preflight are checked again inside the invitation transaction.

Host actions, using the existing endpoint:

- `cue-schedule`: `{blockId}` for an active random block; or `{entryId,requestId,context,characterId,mode}` for a manual control card. Planning a manual card does not block the ongoing show.
- `cue-result-announced`: `{resultId,voiceId}` with the actual ended program receipt.
- `cue-invite`: `{cueId,mode:'prepared'|'ai',characterId}`. The existing call, invitation history and `state.drawHold` are written atomically before ringing. Retrying returns the same call. An unavailable candidate skips the cue without installing a hold.
- `cue-skip`: `{cueId,reason}` before invitation. Once invited, the existing safe return flow is mandatory.
- Player `agree-live`: `{agreed:true}` in backstage/staged. Host `go-live` still requires separate explicit confirmation. Withdrawing the child's consent immediately prevents live or closes the current call.
- Host/player `magic-choice`: `{choice:'stars'|'bubbles'}` after the prepared choice prompt is acknowledged. The first choice wins, including spoken choices entered by regie.
- Output `magic-ready`, `magic-claim`, `magic-played`: the bound output owns playback. Only one claim grants the studio effect; refresh and duplicate requests cannot repeat it. A failed/uncertain claimed effect is reported honestly and is not replayed automatically.
- Host `thank` requests the prepared closing clip; output finishes only after its real ended receipt. `cancel` remains the immediate stop.

Prepared mode is Milo's default. All seven fixed call lines are included for every selectable Milo presenter in the show-audio manifest and loaded by the output after **Audio voorbereiden**. No child name, private notes or backstage recording enters that manifest. The checked name is shown on the control card and broadcast; spontaneous spoken names require explicitly selected live AI. Prepared clips enter the same isolated program mix and the presenter's direct return to the caller; the child's own track is excluded from their return. The optional AI input stays closed in prepared mode. Normal show speech cannot bypass the live-call guard.

Milo's safe snapshot adds `source,mode,cueId,resumeTarget,liveAgreement,magicReadyAt,magic,outroRequestedAt`; its checkpoint also records the original server pause. OBS receives only the fields needed for selected live audio and effects, never family consent, presence, account IDs or regie notes. Refusal/no answer has a distinct `neverEnteredCall` return proof: current audible YouTube plus explicit confirmation that the family stayed watching. A fixed timer never supplies playback evidence. The existing draw hold survives all failures and only the explicit verified resume releases it. A pre-existing manual pause remains in place. The final-round target is ending, never another draw.

## Milo repair contract (current route; supersedes legacy YouTube return checks above)

The original Vlampie flow above remains available only in Vlampie's own environment. Milo uses the same durable call and draw hold, with the following differences:

- Technical preparation is saved for the show and an opaque browser session (`technicalGameId`, `technicalContext`). Presence carries `callPresenceContext` independently and still expires after 45 seconds. The former 30-minute technical TTL does not expire a prepared device during the same show. Older saved checks without a context remain readable; a new check binds a context, and another context must prepare its own microphone before invitation/answer.
- Answer supplies the immutable `checkpointId` and, for a bound check, `technicalContext`. Milo does not require `youtubeMuted`, a second test phrase, heard-number checkboxes, a control word, a live-edge seek, or a return form. The official board remains available. The app never pauses, mutes, seeks, reloads or changes the volume of YouTube in the normal Milo call flow. It asks the parent to lower and later restore the show's volume themselves.
- For a Milo show explicitly using the own programme player (`programBroadcast.enabled`), answer additionally requires `heardLastNumber` matching the immutable checkpoint, `cardsUpdated:true` and `programmeSilenced:true`. The programme player must silence its local mix and end Cast/AirPlay before acknowledging this. This condition does not change the separate-screen YouTube route above or Vlampie's existing flow. See [the programme broadcast contract](program-broadcast-contract.md).
- A real selected guest microphone track must reach the private host connection (`playerTrackReceived` from the real remote-track state) before staging. This is passive connection validation, not a second microphone exercise. Parent `agree-live` and a separate host `go-live {contextConfirmed:true}` remain required. Backstage rooms are revoked before live and cannot feed the program or AI buses.
- After termination the server must positively close issued LiveKit rooms and any AI session (`resourcesClosed:true`). Host `confirm-return {confirmed:true}` then acknowledges safe call closure; host `resume-draw` releases only that call's hold. It does not inspect or manipulate YouTube. Existing manual pauses, windows, results and pending official balls remain protected.
- New standard and premiere templates enable `callFullCardWinner:true` on all four rounds. Missing/false settings on existing plans remain off. Only canonical acknowledged final full-card main-prize results create a winner cue. `announcementScript {version:'milo-winner-v2',resultId,text}` binds the spoken child name and official prize; unsafe speech data uses the generic fixed congratulation. `cue-result-announced` requires that exact text, script version and actual ended output receipt. A bounded missing-ACK state offers an explicit replay or skip instead of automatic repeated speech.
- Winner conversations use only that cue's single `winnerResultId` and immutable confirmed fact. `prepare-winner-greeting` may warm the verified exact greeting while the family is ringing/private; output `winner-greeting` is cache-only. A missing/failed dynamic clip immediately uses the prepared winner-specific congratulation and closing, never the random assistant greeting. Random callers receive no previous winner facts.
- Custom random blocks may freeze `preparedCallLines {greeting,choice,thank,fallback}` and `sourceBlockId` into the existing call. The show-audio manifest preloads those exact source-bound lines for the used presenter. They share the same program and direct-presenter return buses.
- Optional spontaneous AI remains explicitly selected. Detected English phrases close the local AI input/output first; `prepared-fallback` only starts the prepared Dutch dialogue after server-confirmed provider hangup. Transcript detection arrives after audio, so it cannot undo words already heard; prepared Dutch audio remains the dependable default.

`emergency-recover` is a separate authorized host action with `{callId,expectedVersion,reason:'connection-lost'|'audio-stuck'|'cue-stuck',confirmed:true}`. It durably marks `mediaRevokedAt`, mutes guest and AI, forbids new tokens/live starts, revokes issued room participants with `revoke_token_ts`, deletes rooms and retries provider closure. Unknown or unclosed AI creation keeps the hold. After confirmed closure it releases only its own hold when no official window/result/pending commit remains, resets the draw clock, records regie/show/cue/time/reason and returns `{call,game,recovered,blockedBy?}`. Repeating a completed recovery is idempotent. It never cancels the show or draws a ball. These are isolated contract tests, not proof of a real LiveKit/OBS recording.
